The rest of this guide explains loops conceptually. **Field notes** are the evidence: concrete accounts of loops that people ran, what goal they used, what happened and what it cost.

They matter because the evidence base is weak. The [academic review of loop engineering](https://arxiv.org/abs/2608.21884) found claims resting "almost entirely on anecdotes and self-reported productivity numbers". The fix isn't fewer anecdotes; it's **better structured ones**: same fields, real numbers, failures included.

## What a good field note looks like

Every note answers the same questions, so they can be compared:

<Defs
  items={[
    ['The loop', 'What triggers it, what one iteration does, which layer it is (goal, scheduled, graph).'],
    ['The goal', 'The exact completion condition or standing goal. Copy and paste beats paraphrase.'],
    ['The harness', 'Claude Code, Codex, Hermes, Antigravity, OpenClaw, an SDK, or a shell script, plus the model or models.'],
    ['What worked', 'The part you would do again.'],
    ['What hurt', 'Verification, cost, state, review, security, anything. Failures are the most valuable part.'],
    ['Numbers', 'Iterations, wall-clock time, tokens or dollars, success rate. Rough is fine; say so.'],
  ]}
/>

<Callout type="info" title="Why GitHub and not a form?">
  This site intentionally has no accounts, database or submission feature yet. Contributions are pull requests: the
  button above opens GitHub's editor with the template pre-filled. That keeps every note reviewable, versioned and
  attributable while we work out what a structured, comparable format should look like.
</Callout>
